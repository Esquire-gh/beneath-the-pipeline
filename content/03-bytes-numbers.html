03 · How numbers become bytes

This module sits under embed(), long before you get there. That line turns a chunk of text into {{ 03-bytes-numbers.embedding.dims }} numbers, and this module is about what a number is once it has to live in bytes.

From the things you think in, down to bytes

You think in numbers, text, pictures, sound, and video. A disk stores none of those things. It stores bytes, and a byte is eight switches that are each either on or off, which makes it a small number between 0 and 255. That is the entire vocabulary of computer storage. Everything you have ever saved was translated into a row of those small numbers on the way in, and translated back on the way out.

The translation is never automatic. Someone had to sit down and write a rule that says "this kind of information gets written into bytes in this particular way", and those written rules are what file formats are. Module 2 showed you the rule for text, where an agreement says that 65 means A. This module shows you the rules for numbers, and numbers are the key that unlocks everything else, because every other kind of data turns out to be numbers underneath.

Sound is the clearest example, and it is the one you will work with here. To record sound, a microphone measures air pressure {{ 03-bytes-numbers.wav.rate | int }} times every second, and each measurement is a number. A WAV file is those numbers written down one after another, with a short header at the front telling any future reader how to interpret them: how many measurements per second, how many bytes per measurement, how many channels. Images work the same way, since each pixel's color is a few numbers and an image file is those numbers plus a header. Video is images over time with sound alongside. Once you see that each of these formats is "numbers, arranged by a written agreement", the whole zoo of file types collapses into one idea.

A PDF is another such agreement, a far more complicated one, and what it encodes is subtler: what a page looks like. Hold onto that thought, because it explains what "parsing" means in your pipeline. When load() reads a PDF from disk, the thing that arrives in memory is still PDF bytes, the same agreement it was on disk. Loading changes where the bytes are, not what they are. Parsing is the actual conversion: reading bytes under one agreement, the PDF format, and writing the useful part back out under a different agreement, a plain text string. That is all any parser ever does, in any pipeline: it converts data from one agreement to another. Module 5 opens up that conversion for PDFs. This module gives you the skill it depends on, which is reading bytes under a written agreement and knowing what goes wrong when the agreement is misread.

The puzzle

Ask Python whether 0.1 + 0.2 == 0.3 and it answers {{ 03-bytes-numbers.floats.equals_point_three }}. Print the sum and you get {{ 03-bytes-numbers.floats.sum }}.

Here is a second oddity. Store the number {{ 03-bytes-numbers.integer_widths.4.value | int }} in {{ 03-bytes-numbers.integer_widths.4.width }} bytes and it comes back as {{ 03-bytes-numbers.integer_widths.4.stored | int }}, a different number, with no error raised. Store it in {{ 03-bytes-numbers.integer_widths.5.width }} bytes and it comes back unharmed.

Neither of these is a bug. Both are agreements that someone made for you. What are the agreements, and where exactly do they break?

Build it yourself

Open exercises/03-bytes-numbers/starter.py. It has four TODOs, about 40 lines of your own work, standard library only.

1 · Write a hex dump tool, in about thirty lines

You have been reading xxd's output since module 2. Now write your own. It prints three columns: the position in the file, sixteen bytes in hexadecimal with a gap after eight, and those same bytes shown as characters wherever a printable character exists. Printable means bytes 32 through 126, the visible part of module 2's table.

It is a small program, and it forces one thing into the open: you have to decide what to display for bytes that are not text, and nothing in the bytes themselves tells you which ones those are.

The starter writes a WAV file for you with the standard library, so the bytes you parse were produced by something other than the code reading them. Then you read the header, not by guessing, but from the table the format's authors published:

Your parser takes an endian argument. Pass the other value. The bytes on disk do not move. Only your agreement about how to read them changes.

Why it behaves this way

Start with the sample rate, because it is the cleanest case. Four bytes hold the number {{ 03-bytes-numbers.header_correct.sample_rate | int }}. Written low byte first, they are {{ 03-bytes-numbers.hexdump_dump.1.hex.8 }} {{ 03-bytes-numbers.hexdump_dump.1.hex.9 }} {{ 03-bytes-numbers.hexdump_dump.1.hex.10 }} {{ 03-bytes-numbers.hexdump_dump.1.hex.11 }}. Nothing in those bytes says which end to start reading from. That decision is called byte order, or endianness, and it is a convention chosen by whoever designed the format. WAV chose low byte first because it grew up on Intel machines that work that way, and network protocols mostly chose the other end. Neither choice is correct. They are two possible agreements, and a reader has to know which one is in force.

That is why the flipped reading did not raise an error. It produced {{ 03-bytes-numbers.header_flipped.sample_rate | int }}, a perfectly well-formed number that happens to be wrong. The failure mode of a misread agreement is usually not a crash. It is a plausible answer. Module 2 showed the same thing with {{ 02-bytes-text.disagreement.latin1 }}, and this is that lesson repeated in numbers.

The text fields survived the flip because RIFF is four separate one-byte characters. There is no order to reverse inside a single byte, so a run of single bytes reads the same either way. That is worth noticing: byte order is not a property of a file. It is a property of each multi-byte field inside the file.

Why widths exist at all

Now the integers. Python's own integers grow as large as memory allows, so it is easy to forget that this is unusual. Down at the level where data gets stored, a number occupies a fixed number of bytes, decided in advance. One byte can hold {{ 03-bytes-numbers.width_limits.1 | int }} at most. Two bytes can hold {{ 03-bytes-numbers.width_limits.2 | int }}. Four can hold {{ 03-bytes-numbers.width_limits.4 | int }}.

Try to store {{ 03-bytes-numbers.integer_widths.3.value | int }} in one byte and the value that comes back is {{ 03-bytes-numbers.integer_widths.3.stored | int }}, which is the remainder after dividing by {{ 03-bytes-numbers.width_limits.1 | int }} plus one. The high bits had nowhere to go, so they were dropped. This is called overflow, and hardware does it silently, because checking for it would cost time on every arithmetic operation ever performed.

The width is a promise about range, and choosing it is a real decision. Module 9 turns this into a technique: the posting lists inside a search index are lists of integers, and storing each one in the smallest width that fits is where a large part of an index's compression comes from.

Why 0.1 is not 0.1

A 64-bit float stores a number as a fraction multiplied by a power of two. That scheme is called IEEE 754, and every language on your machine uses it. It can represent halves, quarters, and eighths exactly. It cannot represent one tenth exactly, for the same reason base ten cannot represent one third: the digits never terminate.

So when you write 0.1, the machine stores the closest value it can hold, which is:

Slightly more than a tenth. Add it to the closest value to 0.2, and the two small excesses add up to {{ 03-bytes-numbers.floats.sum }}, off by {{ 03-bytes-numbers.floats.error }}. Nothing went wrong. You asked for a number the format cannot hold, and it gave you the nearest one it can, twice.

This sets up a number to carry into Part II. An embedding is {{ 03-bytes-numbers.embedding.dims }} of these approximations. At 32-bit precision that is {{ 03-bytes-numbers.embedding.float32_bytes | int }} bytes per chunk, and at 64-bit it is {{ 03-bytes-numbers.embedding.float64_bytes | int }}. A million chunks is {{ 03-bytes-numbers.embedding.million_float32_bytes | bytes }} against {{ 03-bytes-numbers.embedding.million_float64_bytes | bytes }}, the same vectors held one agreement apart. And every cosine similarity your pipeline computes is a sum of {{ 03-bytes-numbers.embedding.dims }} of these approximations, which is why two mathematically identical ways of computing the same similarity can return slightly different numbers.

How this fits the pipeline

Upward: embed() returns {{ 03-bytes-numbers.embedding.dims }} floats, and you now know what each one is: a fixed-width approximation under a published convention, not a number in the mathematical sense. Backward: modules 2 and 3 are one lesson told twice. Text is a convention over bytes, and numbers are a convention over bytes. Module 6 fuses them, with text going in and numbers coming out, and an agreement standing at each end.

meaning is a convention; arrangement is a cost.

The offsets and widths in that WAV header are pure arrangement. The only reason a parser can find the sample rate is that someone decided in advance where to put it, and that is the same move a search index makes, at a scale you will build in module 7.

If what you saw didn't match

If your hex dump's rows do not match the reference, the usual cause is padding on a short final row: the hex column has to be padded to a fixed width or the right-hand column drifts left. verify.py tests exactly that case and prints both rows so you can line them up.

If flipping endian changes nothing, the argument is probably not reaching struct.unpack_from. Check that the format string is built from it rather than starting with a hard-coded <.

If 0.1 + 0.2 prints as exactly 0.3 in your terminal, you are seeing a shortened display rather than the stored value. Compare with ==, or print repr(), or use Decimal(0.1 + 0.2) to see all of it.
