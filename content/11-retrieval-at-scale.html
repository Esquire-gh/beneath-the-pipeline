11 · How ranking stays fast at scale

This module breaks module 8's scorer. It was correct, and it is about to become the slowest thing in your pipeline.

What this module is about

Module 8's BM25 does its job the honest way: for every document that shares at least one word with the query, compute the full score, then sort. At a hundred thousand passages that was fine. As the corpus grows, the number of documents sharing a word with the query grows with it, and the honest way starts spending almost all of its time computing scores for documents that were never going to matter. You want ten results. It scores tens of thousands of candidates to find them.

The insight this module builds is that you can often prove a document cannot reach the top ten without scoring it. Work out, once, at build time, the largest score each word could ever contribute to any document. At query time, keep the ten best scores seen so far. If a candidate document's words, at their theoretical best, cannot add up to more than your current tenth place, computing its actual score is provably wasted work, and you skip it. Done carefully, this returns exactly the same ten results while doing a small fraction of the arithmetic. It is not an approximation. It is a refusal to compute what cannot change the answer, and it is how real search engines survive their query load.

The puzzle

BM25 scores every document that contains any query term. At {{ 11-retrieval-at-scale.n_passages | int }} passages, a median query's terms cover {{ 11-retrieval-at-scale.postings_per_query.median | int }} postings, and the worst query covers {{ 11-retrieval-at-scale.postings_per_query.max | int }}.

You want ten documents. Most of the ones you are about to score cannot possibly reach the top ten, and you could have known that before scoring them.

How do you skip them without ever skipping one that mattered?

Build it yourself

Open exercises/11-retrieval-at-scale/starter.py. It has three TODOs, in the order the ideas depend on each other.

1 · Score document at a time

Module 8 scored term at a time: take a query word, walk its whole posting list adding to a score map, then take the next word. It works, and it needs a score map holding every document any term touched.

The alternative is document at a time: walk all the posting lists together in document order, finish each document completely, and keep only the best ten. There is no score map, only a heap of ten. It gives the same answers, and it is the shape that makes everything after it possible.

2 · Add skip pointers

Posting lists are sorted. So when you need to reach document 8,000 and your cursor is at 300, you do not have to step through every entry between them. Look ahead a fixed number of entries; if the value there is still too small, move the whole block without reading what is inside it. That look-ahead is a skip pointer, and it costs nothing to have, because the list was already sorted.

3 · Write WAND, which refuses to score what cannot win

Now the idea the module exists for. For each term, compute once at build time the largest score any single document could ever get from it, its upper bound. During a query, keep the ten best scores so far. The tenth is your threshold.

Sort the cursors by the document they are currently at, and add up their upper bounds going down the list. The first point where the running total could exceed the threshold is the pivot. Nothing before the pivot can reach the top ten, whatever its actual scores are, so skip straight to the pivot without scoring anything in between.

Every strategy must return the same answer. The exercise checks this, and it is not a formality. Writing this module produced a version of WAND that was faster and wrong: it counted a repeated query word once while term-at-a-time counted it twice, so the two were scoring different things. The cross-check caught it. The timings would not have.

Why it behaves this way

Start with why the upper bound works, because everything else follows from it.

BM25's score for a document is a sum of per-term contributions. Each contribution depends on the term's rarity, how often it occurs in that document, and the document's length, all of which are known at build time. So for each term you can compute, once, the largest contribution it could ever make to any document. Add those up across a query's terms and you have a ceiling on what any document could score.

Now hold ten scores. If a document's ceiling is below your tenth-best score, its actual score cannot beat it, so scoring it is provably wasted work. You do not need to know what the score would have been. That is the entire argument, and it is why WAND returns exactly the same top ten rather than an approximation. The pruning is sound: it only ever discards documents that could not have won.

Notice how different that is from what module 12 is about to do. WAND gives up nothing, same answers, less work. Approximate nearest-neighbour search gives up correctness for speed. Both are called "making retrieval fast", and only one of them changes your results.

Why the tail is what production teams watch

Your median query got faster. Your slowest queries did not get faster by nearly as much, and relative to the new median they got worse.

The reason is in the mechanism. WAND is fast when the threshold rises quickly: find ten good documents early and the ceiling test starts rejecting almost everything. On a query where the good documents are scattered, or where every term is common so no term has a distinguishing upper bound, the threshold stays low, the pivot barely moves, and WAND degrades towards scoring everything plus the bookkeeping it did trying not to.

So the work per query became far more variable. And a user does not experience your median. A page that issues one search shows the user one query's latency. A page that issues five shows them the slowest of the five, which lands near p99 more often than anyone's intuition suggests. Latency budgets in production are written against p99 or p999 for exactly this reason, and an optimisation that improves the median while stretching the tail can make a system feel worse while every dashboard shows it got better.

What this means for your pipeline

Part 0's retrieve() hides all of this behind a function call. Now you know the questions to ask a search system: does it score document-at-a-time or term-at-a-time, does it prune, is the pruning sound or approximate, and what does its p99 look like, not its median.

How this fits the pipeline

Upward: retrieve()'s cost is not "scoring the corpus". It is scoring the documents you could not rule out, and the ruling-out is the engineering. Backward: module 8 built the scorer this module refuses to run, and module 9's sorted posting lists are what make skip pointers possible at all: the same sortedness that made gaps work.

If what you saw didn't match

If your strategies return different top tens, check two things before assuming a logic error. First, whether they tokenize the query the same way. Counting a repeated query word twice in one strategy and once in another is the bug this module's own solution shipped with. Second, tie-breaking: two documents with equal scores must be ordered the same way by every strategy, which means comparing whole tuples rather than scores alone when replacing the worst entry in the heap.

If WAND scores more documents than document-at-a-time, your threshold is probably never being updated. It should be set to the tenth-best score as soon as the heap is full, and updated on every replacement.

If skip pointers make no difference, check where you are calling them. Advancing to current + 1 can never skip anything, because the next posting is always the next posting. Skipping only pays when the target is far away, which in WAND means advancing a lagging cursor to the pivot.
