02 · How text becomes bytes

This module sits two floors under loader.load(), and directly under every string your pipeline touches. Module 1 said a file is a record and a list of blocks. This module asks what is in the blocks.

What this module is about

You think in text. The disk stores bytes. Something has to bridge the two, and the bridge is not a mechanism. It is an agreement: a table, written down decades ago, that pairs each character with a number. Your pipeline crosses this bridge on its very first line, when loader.load() turns bytes from disk into a string, and it crosses back every time anything gets saved.

The reason to spend a module here is that the bridge can be crossed wrongly, and when it is, nothing crashes. The text that comes out is quietly different from the text that went in, and every later stage, chunking, embedding, retrieval, inherits the damage without knowing. By the end of this module you will be able to look at any file and say exactly which agreement its bytes are written under, and you will know what happens when a reader applies the wrong one.

The mental model: meaning lives outside the bytes

A byte is eight switches. Each switch is on or off, so a byte has {{ 02-bytes-text.byte_settings }} possible settings and no more. That is the entire content of a byte. It is not a number, not a letter, not a colour. It is one of {{ 02-bytes-text.byte_settings }} states.

So where does meaning come from? It comes from outside. Meaning is an agreement between whoever wrote the bytes and whoever reads them. The writer picks a scheme, the reader applies the same scheme, and text appears. Apply a different scheme and different text appears, from the same bytes, and nothing anywhere will complain.

The first agreement: ASCII, where 65 means A

Somebody had to go first. In the 1960s a committee wrote down a table pairing numbers with characters: 65 means A, 66 means B, 32 means a space, and 10 means "start a new line". That table is called ASCII, and it covers 128 of a byte's {{ 02-bytes-text.byte_settings }} settings, which is enough for English, digits, and punctuation, and nothing else.

There is no reason 65 had to mean A. It means A because enough people agreed to act as though it does. In bits, the byte your keyboard sends for A is {{ 02-bytes-text.letter_a.bits }}. Nothing about that pattern is letter-shaped.

The second agreement: UTF-8, for every other character on Earth

The world has more than 128 characters in it. It has well over a hundred thousand. That is a problem, because a byte holds {{ 02-bytes-text.byte_settings }} values, and no arrangement of {{ 02-bytes-text.byte_settings }} values holds a hundred thousand characters.

The solution was to stop using one byte per character. Unicode gives every character a number. The letter é is {{ 02-bytes-text.char_widths.1.codepoint }}, and a brick emoji is {{ 02-bytes-text.char_widths.3.codepoint }}. Then UTF-8 is a scheme for writing those numbers as bytes. Characters that were in ASCII still take one byte and keep their old values, which is why UTF-8 could take over the world without breaking anything. Everything else takes two, three, or four bytes, and the leading bits of the first byte tell a reader how many to expect.

Why "the length of a string" is three different numbers

Once characters take a variable number of bytes, "how long is this text" splits into several questions with different answers.

The word {{ 02-bytes-text.cafe.text }} is {{ 02-bytes-text.cafe.len_characters }} characters and {{ 02-bytes-text.cafe.len_utf8_bytes }} bytes, because the accented letter takes two. Ask Python for its length and you get {{ 02-bytes-text.cafe.len_characters }}. Ask for the length of its bytes and you get {{ 02-bytes-text.cafe.len_utf8_bytes }}. Both answers are right. They answer different questions.

And there is a third number. An astronaut emoji is one thing on your screen. It is {{ 02-bytes-text.astronaut.len_characters }} Unicode characters, a woman, an invisible joiner, and a rocket, and it is {{ 02-bytes-text.astronaut.len_utf8_bytes }} bytes. One glyph, {{ 02-bytes-text.astronaut.len_characters }} characters, {{ 02-bytes-text.astronaut.len_utf8_bytes }} bytes. Three numbers, three questions, and a chunking function that cuts at "500 characters" is quietly picking one of them.

A file format is this same agreement, grown large

Now scale the idea up, because this is the sentence the parsing modules stand on. UTF-8 is an agreement about how to read a run of bytes as characters. A file format is an agreement about how to read a whole file. It is the same idea, with more of it.

A PNG opens with eight fixed bytes that announce what it is, and the specification says exactly how to walk the rest: a length, a four-letter chunk name, the chunk's contents, a checksum, repeat. A PDF opens with %PDF- and a version number, and the PDF specification's rules tell a reader how to walk its objects.

All files are bytes. What makes a PDF a PDF is that the writer and the reader honour the same contract. There is no PDF-ness in the storage. There is a document that follows the rules, and there are programs that know the rules.

Hold onto the second half of that. If a format's rules record what you need, a parser reads it and you get your data. If the rules record something else, say, where to put ink on a page rather than what the words are, then a parser must guess, and no amount of careful reading recovers what was never written down. That is module 5, and module 13 is the full account of why the guessing is hard.

  • The same bytes produced two different texts. {{ 02-bytes-text.disagreement.bytes.0 }} {{ 02-bytes-text.disagreement.bytes.1 }} {{ 02-bytes-text.disagreement.bytes.2 }} {{ 02-bytes-text.disagreement.bytes.3 }} {{ 02-bytes-text.disagreement.bytes.4 }} read as UTF-8 is {{ 02-bytes-text.disagreement.utf8 }}.   • Sometimes it fails loudly instead. Bytes written under Latin-1 and read as UTF-8 give: {{ 02-bytes-text.decode_error }}. That error is not a corrupt file. It is two conventions disagreeing.

Why it behaves this way

Start from the failure, because it is the clearest case. The byte e9 is a perfectly good byte. Under Latin-1 it means é. Under UTF-8 it is the first byte of a two-byte sequence, and the rules say the next byte must begin with a particular bit pattern. It did not. So the decoder stopped, because it could tell that the agreement it was told to apply is not the agreement the bytes were written under.

Contrast that with the pair that did not fail. c3 a9 under UTF-8 is one character, é. Under Latin-1, each byte is its own character, Ã and ©. Both readings are internally consistent, so nothing raised an error, and you got {{ 02-bytes-text.disagreement.latin1 }}. This is the mojibake you have seen on badly configured web pages your whole life, and now you know exactly what it is: two programs holding different agreements about the same bytes.

This is also why "what encoding is this file in" is a question the file usually cannot answer. The encoding is not stored in the bytes. It is what you have to know before the bytes mean anything. Some formats solve this by writing the agreement down inside the file. HTML has a charset declaration, and XML has one in its first line. Plain text has nowhere to put it, so programs guess, and their guesses are where a corpus quietly acquires {{ 02-bytes-text.disagreement.latin1 }} in it.

Now the signatures. A PNG starts with {{ 02-bytes-text.png.signature.0 }} {{ 02-bytes-text.png.signature.1 }} {{ 02-bytes-text.png.signature.2 }} {{ 02-bytes-text.png.signature.3 }} and four more bytes. Those four spell PNG in ASCII, preceded by a byte chosen deliberately to be invalid in most text encodings, so that a program treating a PNG as text fails early and loudly rather than quietly. The convention is designed to be detectable.

That is how file works, and it is why it did not care about the .txt extension in module 1. It holds a table of known openings, reads the first bytes, and reports the first agreement that matches: {{ 02-bytes-text.file_command }}.

Which brings the module to its point. Every stage of your pipeline is one of these agreements, applied. loader.load() decodes bytes to text under an assumed encoding. parse() reads a document under the PDF specification's rules. Even embed() is an agreement, a learned one instead of a standardised one, which is why module 6 introduces it as the same idea with the table filled in by data rather than by a committee.

How this fits the pipeline

Upward: loader.load() hands you a string, and that string exists only because someone chose an encoding on your behalf. When it chooses wrong, your corpus fills with {{ 02-bytes-text.disagreement.latin1 }} and every downstream stage inherits it. Backward: module 1 showed that the disk has no opinion about what a file is. This module says why it does not need one. The opinion lives in the bytes, as a convention two programs share.

meaning is a convention; arrangement is a cost.

This module is the first half of that sentence, stated as plainly as the site ever states it. Module 3 does the same for numbers, and then module 6 fuses them: text in, numbers out, an agreement at each end.

If what you saw didn't match

If your terminal shows boxes or question marks instead of {{ 02-bytes-text.char_widths.2.char }} or {{ 02-bytes-text.char_widths.3.char }}, the bytes are still correct. Your terminal font has no picture for that character. Check len(ch.encode()) in Python instead of trusting the display; the number is the evidence, the glyph is not.

If xxd is missing, use hexdump -C. The columns are laid out slightly differently and the byte values are identical.

If raw.decode("latin-1") raises instead of printing {{ 02-bytes-text.disagreement.latin1 }}, you are decoding different bytes than the exercise did. Latin-1 maps all {{ 02-bytes-text.byte_settings }} byte values to characters and cannot fail. Check that raw came from .encode("utf-8").
