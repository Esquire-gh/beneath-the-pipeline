What an index is, and why every search engine has one

There are two ways to answer the question "which of these {{ 07-index.n_passages | int }} passages mention the word block". The obvious way is to read all of them, every time someone asks. The other way is to do that reading once, in advance, and write down the answer for every word at the same time, in a table that maps each word to the list of passages containing it. After that, answering the question means looking up one entry in a table.

That table is called an inverted index, and the list of passages under each word is called a posting list. The name "inverted" describes the flip it performs: documents are stored as "this document contains these words", and the index turns that around into "this word appears in these documents", which is the direction questions actually come from. It is the same move the filesystem made in module 1, where bookkeeping written in advance made a name cheap to resolve. Here, bookkeeping written in advance makes a word cheap to find.

Your pipeline's db.add() built a second structure too: an array of module 6's vectors, arranged so that a query vector can be compared against all of them. In this module you build both structures yourself, measure what they cost to build and to hold, and measure what they give back per query.

The puzzle

Find every passage containing the word block among {{ 07-index.n_passages | int }} passages by reading all of them. That takes {{ 07-index.scan.block.seconds | time }}.

Ask the same question of an index and the answer comes back in {{ 07-index.lookup.block.seconds | time }}.

Nothing about the corpus changed. What exactly did the index precompute, and what did precomputing it cost?

Why it behaves this way

An index is arrangement. That is the whole definition. You do work in advance to put things where a question can find them, and in exchange the question gets cheap.

Follow where the work went. Building the inverted index took {{ 07-index.inverted.build_seconds | time }}. It tokenized every passage, which is exactly what the scan does, but it did so once instead of once per query, and then it wrote the answer down in a shape a lookup can reach directly. The scan repeats that work on every question. The index did it once and kept the result. The {{ 07-index.lookup.block.speedup | x0 }} is not cleverness. It is the scan's work, moved to a moment when nobody was waiting.

Which is why the cost shows up in three places, and you measured all three:

  • Time, paid once. {{ 07-index.inverted.build_seconds | time }} before any query can run.
  • Memory, paid continuously. {{ 07-index.inverted.size_bytes | bytes }}, which is more than the corpus itself, held for as long as you want fast answers.
  • Currency, paid on every change. The index describes the corpus as it was when you built it. A new document does not appear in any posting list until something puts it there, and that is module 10's entire subject.

The two structures answer different questions

Look at what the two structures actually organise, because they are not two implementations of one idea.

The inverted index maps words to locations. It answers "which documents contain this token" exactly, and it can answer nothing about a word it has never seen. Ask it for zyzzyva and it says {{ 07-index.scan.zyzzyva.hits | int }}, correctly and instantly.

The vector array arranges points for distance. It answers "which documents are nearest this one" approximately in meaning and exactly in arithmetic, and it always returns ten things. There is no such thing as no match, because every point has neighbours. Ask it for nonsense and you get the ten nearest pieces of nonsense.

Those are different failure modes, and neither is a defect. A word index cannot find a paraphrase, and a vector index cannot tell you that a term is absent. Module 15 fuses them precisely because their weaknesses do not overlap.

What db.add() was doing

Now go back to Part 0's line. db.add(ids=…, embeddings=…, documents=…) built exactly these two things: somewhere to look up documents, and an arrangement of points for distance search. It chose the arrangement, the distance measure, the memory layout, and how much accuracy to trade for speed, silently, on your behalf, with defaults that are somebody's answers to questions you can now ask.

How this fits the pipeline

Upward: db.add() has no magic left in it. It is a table of words to locations, and an array of points. Backward: module 1's filesystem keeps bookkeeping so that a name becomes cheap to resolve. If what you saw didn't match

If your lookup time is reported as 0, you timed one lookup. A single dict access is faster than the clock can resolve. Time {{ 07-index.lookup_reps | int }} of them and divide, which is what the solution does.

If your index is much smaller than {{ 07-index.inverted.size_vs_corpus | x }} the corpus, check whether you are storing each passage id once per occurrence rather than once per document. Using a set per document before extending the posting list is the fix, and it is why the TODO says each id appears once.

If your speedups are far below {{ 07-index.lookup.block.speedup | x0 }}, your scan may be using a substring search rather than tokenizing. That is a fair thing to do, and it is roughly ten times quicker. It also answers a different question, as the block row shows.
