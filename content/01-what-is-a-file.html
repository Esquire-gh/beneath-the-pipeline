01 · What is a file, actually?

This module sits three floors under loader.load(). Your pipeline's first line opens PDF files, and before you can say what opening one costs, you have to say what a file is.

What this module is about

You use files every day, and you carry a picture of them in your head: a file is a thing with a name, a size, and an icon, sitting in a folder. That picture is drawn for you by the operating system, and it hides almost everything about how the thing actually works. This module replaces the picture with the machinery underneath, because the machinery is what your pipeline pays for.

The short version, which the rest of the module earns: a disk only stores bytes, in fixed-size batches. Everything else you associate with a file, its name, its size, its type, the folder it lives in, is bookkeeping that the operating system writes onto the same disk, next to your data. Once you can see the bookkeeping as a separate thing from the bytes, a whole family of confusing behaviors becomes predictable: files that take more space than they contain, deletes that free no space, gigabyte files that occupy almost nothing, and load times that depend on how many files you have rather than how much data.

The puzzle

Write three characters into a file. Ask your system how big the file is and it says 3 bytes. Ask how much disk the file takes and it says {{ 01-what-is-a-file.three_char.allocated | int }} bytes.

Both answers come from the same operating system, about the same file, at the same moment. Where did the other {{ 01-what-is-a-file.three_char.allocated | int }} minus 3 bytes go?

The mental model: a disk, and a database about it

A hard disk or SSD does not know what a file is. It knows one thing: it has a very long row of numbered slots, and you can ask for the contents of a slot or ask to put something in one.

The slots are not individual bytes. The disk hands out its contents in fixed-size batches. {{ 01-what-is-a-file.alloc_block_size | int }} bytes is a common size, and it is the size on this machine. Such a batch is called a block, and it is the smallest amount of disk a file can occupy. If you want to store one byte, you get four thousand and change, and the rest sits unused.

So the disk is a row of numbered blocks and nothing more. No names, no folders, no file types, no dates. Which raises a question: you have a folder on your screen with files in it that have names and sizes and icons. Where is any of that?

The answer is that it is on the disk too, written into some of those same blocks. Some blocks do not hold your documents. They hold bookkeeping about your documents: which blocks belong together, what name points at them, how they should be read. Think of it as a small database the operating system keeps about your bytes. That bookkeeping scheme is called a filesystem. The files and folders you see on your desktop, on a Mac or on Windows alike, are not things sitting on a disk. They are that database, drawn on a screen.

Every file is a record in that database

The database has one central kind of entry. For every file, the filesystem keeps a small record holding the file's size, who owns it, when it was last changed, and, the part that matters here, the list of block numbers holding its contents. That record is called an inode. It has a number, and that number is how the filesystem refers to the file internally.

Read that list again and notice what is missing from it. The record holds the size, the dates, the owner, and the blocks. It does not hold the name.

The name lives in the folder, not in the file

The name lives in the folder. And a folder, it turns out, is a file too: a file whose contents are a list of pairs, each pair being a name and a record number. That is all a folder is. When you ask for report.pdf, the operating system reads the folder's contents, finds the pair whose name is report.pdf, takes the record number next to it, reads that record, gets the list of blocks, and asks the disk for those blocks.

This has a consequence you can see with two commands, and it is the payoff of this module: the name and the contents are separate things. They are stored in different places, they are edited by different operations, and either one can exist without the other making any sense.

Two names can point at the same record. Then the file has two names, both equally real, and there is no fact of the matter about which one is "the" file. Deleting a name removes one pair from one folder's list, and it does not touch the bytes. The bytes go away when the last name pointing at them is gone and the record says nobody is looking any more.

The record has no "type" field

One more thing is missing from that record: what the file is. There is no type field. A photo, a PDF, and a program are, on disk, a record and a list of blocks, with no difference in kind. The .pdf at the end of a name is part of the name, a hint to humans and to programs that trust hints. Rename it and nothing underneath changes, because there is nothing underneath to change.

What makes a PDF a PDF is not where it lives or what it is called. It is that the bytes inside follow a convention that a reader can honour. That sentence is module 2's whole subject, and it is the floor the parsing modules stand on.

Why a retrieval pipeline cares

Everything above is why a call like loader.load() has a cost that has nothing to do with how many bytes you asked for. Reading a file means reading a folder, reading a record, and then asking for blocks. That is three trips before a single byte of your document arrives. Do it for ten thousand files and you pay for ten thousand folder lookups and ten thousand records. Module 4 measures exactly that.

And storage engines, the things inside every database and every vector store, mostly decline to play this game. They keep one enormous file and do their own bookkeeping inside it, because the filesystem's bookkeeping is arranged for a different access pattern than theirs. You will build that kind of bookkeeping yourself in module 10.

Investigate it yourself

Every command below runs on macOS and Linux, and where the two differ, both are shown. On Windows, use WSL. Work in a scratch directory, for example mkdir /tmp/floor && cd /tmp/floor, because you are about to make a file that claims to be a gigabyte.

Or run all of it at once, which also records the numbers this page prints:

1 · See the gap between size and space

macOS
$ printf 'abc' > three.txt
$ stat -x three.txt
$ stat -f %k .
Linux
$ printf 'abc' > three.txt
$ stat three.txt
$ stat -f -c %s .

Read the size and read the blocks. The size is 3. The blocks are counted in 512-byte units, so multiply them out: this machine reserved {{ 01-what-is-a-file.three_char.allocated | int }} bytes for three characters. Say the gap out loud: {{ 01-what-is-a-file.three_char.allocated | int }} reserved, {{ 01-what-is-a-file.three_char.size }} used.

2 · Append a character and watch which number moves

The size moves from 3 to 4. Watch what the blocks do. Then find the edge: write a file of exactly {{ 01-what-is-a-file.alloc_block_size | int }} bytes, then one of {{ 01-what-is-a-file.boundary.at_block_plus_1.size | int }}, and compare the two.

3 · Give one file two names

Both names show one record number. Which one is "the" file?

4 · Delete one of the names

The other name still works. Ask yourself what rm actually removed.

5 · Make a file that claims a gigabyte

macOS & Linux (coreutils)
$ truncate -s 1G big.img
$ ls -l big.img
$ du -h big.img
macOS without coreutils
$ mkfile -n 1g big.img
$ ls -l big.img
$ du -h big.img

ls reads the size field in the record. du adds up the blocks. They disagree by a gigabyte.

6 · Rename a PNG and see who notices

file gives the same answer both times, because it never looked at the name. It looked at the first few bytes.

Four things to have seen:

  • The gap. Three characters reserved {{ 01-what-is-a-file.three_char.allocated | int }} bytes, which is one whole block. The disk will not hand out less.
  • Size moved, blocks didn't. Appending a character changed the size field in the record and nothing else, because the byte fit in a block that was already reserved. The reservation moves at exactly one byte past the block: at {{ 01-what-is-a-file.boundary.at_block.size | int }} bytes of content the file still holds {{ 01-what-is-a-file.boundary.at_block.allocated | int }} bytes of disk, and at {{ 01-what-is-a-file.boundary.at_block_plus_1.size | int }} it holds {{ 01-what-is-a-file.boundary.at_block_plus_1.allocated | int }}.
  • Two names, one record. After ln, both names showed the same number and the record said {{ 01-what-is-a-file.hardlink.link_count }} names point here. After rm it said {{ 01-what-is-a-file.after_unlink.links }}, and the surviving name still read the same bytes.

And here is the ratio to keep, because your pipeline lives in it. The corpus in data/corpus_small/files holds {{ 01-what-is-a-file.corpus.size | bytes }} of text in {{ 01-what-is-a-file.corpus.files | int }} files averaging {{ 01-what-is-a-file.corpus.mean_file_size | bytes }} each. Those files reserve {{ 01-what-is-a-file.corpus.allocated | bytes }} of disk, which is {{ 01-what-is-a-file.corpus.waste_ratio | 2f }}× the text, because every file rounds up to a whole number of blocks.

Why it behaves this way

Work backwards from the gap. Three characters took a whole block because a block is the unit the hardware trades in. The filesystem cannot reserve part of one, so it reserves one, writes three bytes into the front of it, and records in the file's own record that the useful length is 3. Two numbers are doing two different jobs: one says how much space is held, and the other says how much of that space means anything.

That is also why the fourth character was free. The block was already yours. The write went into space already reserved, and the only thing that changed was the length field. Fill the block exactly, all {{ 01-what-is-a-file.boundary.at_block.size | int }} bytes of it, and you still hold one block. Write one more byte and you hold {{ 01-what-is-a-file.boundary.at_block_plus_1.allocated | int }}. The reservation does not grow gradually. It doubles in a single step, because half a block is not a thing the hardware trades in.

Now the gigabyte. truncate set the length field to a billion and wrote nothing. ls -l printed the length field, so it reported a gigabyte. du added up the blocks, found almost none, and reported almost nothing. Neither tool is lying. They read different fields, because a file's stated length and its actual occupancy were never the same fact. Files like this are called sparse, and they are how a virtual machine can have a 500 GB disk image on a 256 GB laptop.

The hard link is the sharpest of the four. ln did not copy anything. It added one pair, a name and a record number, to a folder's list, and bumped the count in the record that says how many names point here. Two entries, one record, one set of blocks. Nothing in the system marks one as the original, because nothing in the system needs to. rm removed a pair from a list and decremented the count. The contents only become free when that count reaches zero.

Which is why "the file" is a slightly wrong idea. There is a record, and there are names pointing at it. Usually there is one name, and the shorthand does no harm, until you meet a link, or a delete that frees no space, and the shorthand stops predicting what you see.

Then the rename. Nothing about a file's contents is recorded anywhere except in the contents. The .png was a hint in a folder's list. file ignores hints. It reads the first bytes and compares them against a table of known openings, and the bytes it found, 89 50 4e 47, are the PNG signature that the PNG specification says every PNG starts with. The name changed, the bytes did not, and only one of those two things was ever the evidence.

All of which sets up the number you will care about most. Your corpus wastes {{ 01-what-is-a-file.corpus.waste | bytes }} on block rounding, but that is the small cost. The large one is that opening each of those {{ 01-what-is-a-file.corpus.files | int }} files means walking this machinery from the top: find the folder, read the list, get the record, get the block list, ask for blocks. Ten thousand times over. Module 4 puts a stopwatch on it.

How this fits the pipeline

Upward: loader.load() now has a floor under it. It does not "get the file". It consults a database the operating system keeps about your bytes, and then asks the hardware for specific numbered blocks. Backward: there is nothing behind this module yet, because it is the floor. Ahead, the same move repeats at bigger radius three times: the filesystem keeps bookkeeping so a name becomes cheap to resolve, module 7's index keeps bookkeeping so a word becomes cheap to find, and module 14's tables keep bookkeeping so a total becomes cheap to compute.

meaning is a convention; arrangement is a cost.

Both halves of that sentence are already here. The bytes 89 50 4e 47 mean "PNG" only by agreement. The block is the cost of arranging anything at all.

If what you saw didn't match

If stat reports blocks that don't multiply out to a multiple of {{ 01-what-is-a-file.alloc_block_size | int }}, your filesystem may store very small files inside the record itself rather than in a separate block. APFS, ext4 and Btrfs all do a version of this. The gap is then smaller than shown here, and the lesson is unchanged: the length field and the occupancy are separate facts.

If ln fails with "Operation not permitted", you are probably on a filesystem that doesn't support hard links, such as an exFAT or FAT32 drive. Run it under /tmp instead.

If du reports the full gigabyte, your filesystem does not do sparse files, and some do not. Compare ls -l against du on a normal file instead: they will agree, and that agreement is the thing to notice.
