05 · Parse — how a PDF becomes text

This is the pipeline line every tutorial spends one line on. page.get_text() looks like reading a field out of a file. It is not.

What parsing is

Module 3 gave you the definition, and this module puts it to work. Every file is bytes written under some agreement, and parsing is converting data from one agreement to another. After load(), what sits in memory is still PDF bytes, organized exactly the way the PDF format says. Your pipeline needs something different: a plain string of text, in reading order, under the much simpler agreement that module 2 described. parse() is the conversion between those two.

How hard that conversion is depends entirely on what the source agreement wrote down. For a format like CSV or JSON, the structure you want is recorded in the bytes, so a parser follows the rules and the answer comes out the same every time, from every correct parser. You will write one of those in this module, in twenty lines, to feel what that is like. Then you will open a PDF and discover that its agreement recorded something else entirely, which is why this stage of the pipeline, alone among the six, gives different answers depending on which library you picked.

The puzzle

Take one PDF, acl-2col-01.pdf, an ordinary conference paper. Extract its text twice, using two well-maintained, widely used libraries, and compare what comes out.

One library returns {{ 05-parse.extractions.acl-2col-01.words_a | int }} words. The other returns {{ 05-parse.extractions.acl-2col-01.words_b | int }} words. The character similarity between the two outputs is {{ 05-parse.extractions.acl-2col-01.char_ratio | 3f }}, and the differences are not formatting. They are different words, in a different order, from the same bytes.

Neither library has a bug. How can two correct programs disagree about what a file says?

Why it behaves this way

Parsing is honouring the writer's agreement, and the whole difficulty of this stage is that some agreements record less than you need.

CSV records structure. The commas are the field boundaries, and the quoting rules are how ambiguity gets resolved. Two correct CSV parsers cannot disagree about where a field ends, because the format wrote it down. The same holds for JSON, for HTML, and for XML. You get determinism because the structure is in the file.

PDF records presentation. Its agreement is complete and precise. The specification runs nine hundred pages, and PyMuPDF honours it faithfully. But what it specifies is where glyphs go on a page. Reading order is not stored. Word boundaries are not stored. Paragraphs are not stored. A table is some numbers positioned near some lines, and the lines are drawing commands, unconnected to the numbers.

So a PDF text extractor cannot read the structure. It has to reconstruct it, from coordinates, gaps, and font sizes. Should two runs of glyphs 4 points apart be one word or two? Is that block at the top a heading, or a running header to discard? Do these two columns of coordinates mean two columns of text, or one wide table?

Every one of those is a judgement call, and the two libraries make different ones. That is the entire explanation for the table above. Neither library is broken. They have different heuristics for a problem the format left open, and the more visual structure a document carries, the further apart their answers land. That is exactly the shape of the chart: the clean page at {{ 05-parse.extractions.gen-clean-1col.char_ratio | 3f }}, the table page at {{ 05-parse.extractions.gen-tables.char_ratio | 3f }}.

Two things follow, and both are load-bearing for the rest of the site.

First, "parse the PDF" is not one operation with a right answer. It is a reconstruction with a quality, and the quality varies by document. Any pipeline that treats parse() as a settled step has an unmeasured variable in it. Module 15 measures that variable and finds it larger than the retrieval architecture.

Second, this only gets harder. Everything above assumed the glyphs are in the file at all. When a document has been scanned, the page is a picture, there are no glyphs, and there is nothing to reconstruct from. Why that situation is genuinely hard, and what it takes to do well in it, is module 13's whole subject.

How this fits the pipeline

Upward: parse() is not extraction, it is reconstruction, and it returns one library's opinion. Backward: module 2 said a file format is an agreement grown large, and that a parser can only recover what the agreement recorded. This module is the first time that sentence costs you something.

meaning is a convention; arrangement is a cost.

Here both halves bite at once. The convention was honoured perfectly and still did not carry the meaning, because the meaning was in the arrangement of ink, and arrangement is exactly what a reader has to pay to reconstruct.

Read further, then check yourself

The PDF specification (ISO 32000), the content-stream section. An afternoon that permanently explains why extraction is hard. Read the text-showing operators, Tj, TJ, Td, and Tf, the ones you just watched go past in the dump above, and notice what the operator list does not contain.

There is no canonical book for this stage of the pipeline. That is worth saying plainly: the line your pipeline spends the least time on is the one with no textbook behind it. Module 13 uses papers, because papers are the literature.

  3. A table in your corpus comes out as a run of numbers with no columns. What was stored in the file, and what was not?
If what you saw didn't match

If your similarity on the clean document is below about 0.95, check whether pdfplumber returned None for a page. It does that on pages with no extractable text, and joining None as an empty string quietly shortens the output. The starter's plumbing already guards for this.

If both libraries return exactly the same text on every document, you are probably testing only single-column, generated PDFs. Add a real paper, such as acl-2col-01.pdf in data/hard_pdfs/, where the layout decisions are real.

If count_word_in_raw_bytes returns a number greater than zero, your PDF may be uncompressed. Some tools write PDFs with plain-text content streams. The words are then findable, and the rest of the module's argument is unchanged, because what you would find is still Tj commands rather than sentences.
