10 · Keeping the index fresh as documents arrive

This module breaks module 7's "build it once" assumption, and it sits under every db.add() that happens after the first one.

What this module is about

Module 7 ended on a warning: an index describes the corpus as it was at the moment you built it. Real corpora do not hold still. Documents arrive every hour, get corrected, get deleted, and every one of those events makes the index a little more wrong until something updates it.

Updating it turns out to be a genuinely hard problem, because the two obvious approaches both fail. Rebuilding the whole index from scratch on every batch of new documents costs the full build price, forever, for corpora that mostly did not change. Editing the existing index in place fails for a mechanical reason you already know: posting lists sit packed together in a file, and growing one in the middle means moving everything after it.

The industry's answer is a third way, and this module has you build it. Never edit anything. Each batch of new documents becomes its own small, self-contained index, called a segment, written once and never touched again. Queries consult every segment and combine the answers, and a background process occasionally folds small segments into bigger ones to keep that consultation cheap. The whole design is a dial between write cost and read cost, and you will measure both ends of it. Then, because segments live on disk across program restarts, you will design the file format they are stored in, and discover what it takes for a file written by last week's code to remain readable by next week's.

The puzzle

New documents arrive. Rebuilding the whole index takes 610.9ms at this scale, which is 10× the cost of indexing one batch, and you would pay it on every batch, forever.

Appending to the existing index in place is somewhere between hard and impossible, because every posting list would need to grow in the middle of a file.

Meanwhile, the index you saved with pickle last week will not load in this week's code.

How does a search engine accept new documents every minute without ever paying for a rebuild?

Build it yourself

Open exercises/10-ingestion-vs-query/starter.py. It has four TODOs: three about accepting new documents without rebuilding, and one about writing an index down so a later version of your code can still read it.

Write segments, and never edit them

Each batch of documents becomes its own small index, written once and never modified. A delete becomes a note saying "ignore this document". An update becomes a delete plus an add. Nothing is changed in place, ever.

That makes writing cheap and reading more expensive, because a query now has to consult every segment and combine the answers. The number of segments a query touches is called the fanout. Controlling it is what a merge policy is for: whenever several segments of about the same size exist, fold them into one bigger segment in the background.

Then design the file format they live in

Module 3 said reading a field needs three facts: offset, width, and byte order. Now you are the format author, so you have to write those facts down: a magic number to say what the file is, a version number, and a layout. Then you get to find out what happens when the format changes.

What you should see

What fanout costs

The comparison has to hold the corpus constant, or you measure corpus size instead of segment count. Here the same 50,000 documents are cut into different numbers of segments, each written to its own file in the format you designed, and queried by seeking into it, which is what a real segment is.

There are two effects here, and the smaller one is the famous one.

Query time grew 1.1× going from 1 segment to 50, because each segment is another seek: module 4's border crossing, once per segment per term. That is a real cost and a modest one here, on a local SSD with term dictionaries already in memory. Put those segments on network storage, or make the term dictionary too large to keep resident, and the same 41 reads per query stop being cheap. The measurement is honest about this machine, and the mechanism is what travels.

And the index got 1.6× bigger: 8.8MB as one segment, 13.8MB as 50. Every segment repeats the whole term dictionary. The word the is stored fifty times, once per segment, along with every other term that appears in more than one batch. Fanout costs space before it costs time.

The fastest queries come from fan=3. The cheapest ingestion comes from never merge. They are not the same policy, and no amount of engineering makes them the same policy, because the merge that makes a query cheap is the work that makes ingestion expensive.

Look at the rewritten column. Merging aggressively rewrote 226,000 documents' worth of postings, several times the corpus, because a document that gets merged twice is written twice. Never merging rewrote nothing and left 50 segments for every query to visit.

And whether the file survives your own code changing

the four ways a reader and a file can meet
readerdatawhat happens
version 1version 1 reads it
version 1version 2 refuses: index was written by version 2; this reader understands up to 1. Refusing to guess.
version 2version 1 reads it, 0 document lengths (none, correctly)
version 2version 2 reads it, 200 document lengths

All four behave deliberately. The old reader refuses new data rather than misreading it, because the version number is the second field in the file and it checks it before anything else. The new reader accepts old data and correctly reports that there are no document lengths in it, because the flag says so. Version 2 added its field by appending a section rather than inserting one, which is the only reason any of this works.

Compare with what you get for free:

pickle of the same segment: 926.8KB, which is 0.8× the size of your format. And pickle stores the class path. Rename or move the Segment class and every saved index becomes unreadable, with no version number to tell you why.

Why it behaves this way

Everything in this module follows from one decision: never modify a file that has been written.

The reason to make that decision is what module 4 measured. Editing a posting list in the middle of a file means moving everything after it, and files do not have room in the middle; module 1's block list is not a linked list you can splice. Appending is cheap, and inserting is a rewrite. So systems that must accept writes continuously stop inserting and start appending, and then spend their engineering budget on the consequence.

The consequence is that reads fan out, and the fix for reads is to periodically rewrite many small files into one large one. Which is a write. So the whole design is a dial: turn it towards reads and you pay in write amplification, turn it towards writes and you pay in fanout. You measured both ends of the dial and the shape between them.

That structure has a name, a log-structured merge tree, LSM for short, and you have now derived it rather than memorised it. It is how Lucene, Elasticsearch, RocksDB, Cassandra, and every vector database that accepts live updates handles ingestion. When a vector database's documentation talks about segments, compaction, or a flush interval, it is talking about the dial you just turned.

Why the format half belongs here

Because an index you cannot reload is an index you rebuild, and rebuilding is the thing this whole module exists to avoid.

The temptation is pickle, and it is a trap with a specific shape. Pickle stores the path to your class. Rename Segment, move it to another module, or change its fields, and every index you ever saved becomes unreadable, with no version number to explain why and no way to write a converter, because you cannot read the old data to convert it.

Your format cost about forty lines and gives you something pickle structurally cannot: a file that says what it is. Four magic bytes so a reader can tell this is your index and not a JPEG. A version number so an old reader refuses rather than guesses. A flags field so a new section can be optional. This is module 2's argument with you on the other side of it. You are the one writing the agreement down, and everything you leave out is something a future reader will have to guess.

How this fits the pipeline

Upward: the second and every subsequent db.add() is this: a new segment, a merge policy deciding what to fold together, and a format on disk that a later version has to still understand. Backward: module 4 said appending is cheap and rewriting is not; module 7 built the index that this module stops rebuilding; module 3's offsets and widths are now yours to publish.

meaning is a convention; arrangement is a cost.

Both halves, in one module, and this time you are the author of the convention.

Read further, then check yourself

Petrov, Database Internals, Part I. LSM trees, compaction strategies, and the read/write amplification vocabulary for the dial you just turned. Expect it to name the two ends, size-tiered and levelled compaction, and expect to recognise your fan parameter in both.

Kleppmann & Riccomini, Designing Data-Intensive Applications, 2nd edition, "Encoding and Evolution". For the persistence half. Expect it to be blunter than this page about language-specific serialisation, and to give you the terms, backward and forward compatibility, for the four rows of that matrix.

  1. Your merge policy has fan = 4. A batch arrives every minute. Sketch what the segment count does over an hour, and say when the expensive merges happen.
  2. Slicing the same corpus into 50 segments made the index 1.6× bigger. Where did the extra bytes go, and would compressing the postings help?
  3. You add a field to your format. Name the change that lets old readers keep working and the change that must break them, and say how a reader can tell the difference.
If what you saw didn't match

If query time barely moves as segments accumulate, check that you are querying files. An in-memory dict of segments genuinely does not care how many there are, because total postings are the same however you slice them, and measuring it that way makes fanout look free. The cost lives in the per-segment seek, so it only appears when segments are on disk.

If your merge policy never merges anything, check the tier calculation. Segments are bucketed by log(n_docs, fan), so segments of equal size land in the same tier. If you bucket by exact document count, batches that differ by one document never merge.

If your version-1 reader happily reads version-2 data, it is not checking the version field. That is the failure the whole exercise exists to make you cause once: it will read the postings correctly and then silently ignore everything after them, which is worse than crashing.
