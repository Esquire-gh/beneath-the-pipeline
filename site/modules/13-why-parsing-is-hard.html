Part III · module 13 · investigate & build · 60–90 minutes

13 · Why parsing is a hard problem

This module pays off the thread module 5 opened. The pipeline line with no canonical book behind it finally gets its mechanisms, four of them.

What this module is about

Module 5 established what parsing is: converting a document from the agreement it was written under into the plain text your pipeline needs. It also showed the first crack, that a PDF records where ink goes rather than what the text says, so extraction is reconstruction. This module goes the rest of the way down, because the crack widens into four separate mechanisms, and each one fails differently.

First, many PDFs contain no text at all. A scanned document is a photograph of a page, and a parser honouring the PDF specification perfectly will find nothing in it. Second, the fix for that, optical character recognition, is a model guessing characters from pixels, and its guesses are wrong in measurable amounts that depend on scan quality. Third, even when the text is present, the structure is not: reading order, columns, and tables are all inferences from coordinates, and they fail on styling choices as small as whether a table's grid lines were drawn. Fourth, the modern answer to all of this, vision models that read the page the way a person does, costs orders of magnitude more compute per page, which is why serious document pipelines want a GPU. You will measure each mechanism on documents built to isolate it.

The puzzle

Here are two PDFs. On screen they are indistinguishable: same layout, same words, same table. Open them side by side and you cannot tell which is which.

Run the same parser over both. One returns 1,903 characters. The other returns 0.

How can two documents that look identical to a human behave that differently to a program?

Build it yourself, then run the experiments

This module is mostly investigation: run the solution and read what happened. But three functions are worth writing yourself first. Two of them are how every accuracy claim below is computed, edit distance and the character error rate built from it. The third is the one to take to work with you: a function that decides whether an extraction failed. Module 15 uses all three.

Then come four investigations. Each one is a mechanism, and together they are the reason "parse this PDF" is not one operation.

(a) A scanned page contains no text to find

The repository builds the matched pair for you, and how it does it is the whole explanation: it takes a clean text PDF, renders each page to a picture, and wraps the pictures back into a PDF. That is exactly what every office scanner and every "print to PDF" button on a photocopier does.

measured by exercises/13-why-parsing-is-hard/solution.py
documentcharacters extracted file size
gen-clean-1col.pdf 1,903 3.4KB
gen-clean-1col-scanned.pdf 0 6.0MB
gen-tables.pdf 1,794 4.0KB
gen-tables-scanned.pdf 0 12.0MB

That is not "worse extraction". It is nothing at all, from a file 1,819× larger.

This is module 2's lesson at document scale. The bytes now honour an image agreement: a grid of pixel values, with rules for compressing them. The words exist only as patterns of dark pixels that a human eye decodes. There are no glyphs, no fonts, and no Tj commands. Module 5 showed you what a text PDF's page holds, and none of it is here. A parser honouring the PDF specification perfectly finds no text, because there is no text.

(b) OCR guesses at the pixels, with a measurable error rate

Optical character recognition is a model that looks at pixels and predicts characters. It does not recover the original text. It makes a fresh guess at what the shapes say, and its guesses are wrong in measurable amounts.

The measure is character error rate: the number of single-character edits, insert, delete, or substitute, needed to turn the OCR output back into the true text, divided by the true text's length. Zero is perfect.

documentcharacter error rate words foundseconds per page
a clean 150 dpi scan 0.0005 99.7% 951.7ms
ruled tables, dense small numbers 0.0151 92.8% 563.9ms
120 dpi, skewed, speckled 0.1277 85.8% 1.02s

On a clean scan, OCR is close to free: 0.0005 error rate, 99.7% of words recovered. It is genuinely a solved problem for clean printed text, and it has been for years.

Then take the resolution down to 120 dpi, tilt the page by under a degree, and add speckle, a photocopy of a photocopy, which is what a great deal of the world's archived paper actually looks like. The error rate goes to 0.1277. That is 243× the error rate of the clean scan, from the same engine with the same settings.

Look at where the errors land in the table scan, because the pattern is the point:

Errors cluster where the visual evidence is thinnest: small type, digits, which have less shape to distinguish them than letters, and text touching a ruling line. A document that is mostly prose OCRs beautifully while the one table in it, the part somebody wants to ask a question about, is the part that came back wrong.

(c) Reading order and tables are guesses about layout

Now assume the text is in the file. Structure still is not.

Reading top to bottom by coordinate, the pen visits the left column and the right column alternately, so the sentences interleave. Every word is present. The document is unreadable.

The page never stored "this is a column". Columns are a visual convention that a human reader infers from a gap of whitespace. A parser has to infer it too, from coordinates, and whether it does depends on a setting most people never see.

Tables are worse, because detection comes before extraction

documenthorizontal rules vertical rulestables found rows extracted
gen-tables.pdf 8 0 0 0
gen-tables-ruled.pdf 32 21 3 29

Same numbers. Same column arrangement. Same font. A person reads both as tables without hesitating. The difference is that one is drawn with a full grid and the other with three horizontal rules and no verticals, a styling choice made by whoever wrote the document, years ago, for aesthetic reasons.

The library finds 29 rows in one and 0 in the other, because its table finder works by looking for ruling lines. The undetected page still extracts as text. It comes out as a stream of numbers with no row or column structure, and a chunker will cut it wherever the character count runs out, which is module 6's table disaster arriving on schedule.

(d) Why the good models want a GPU

Rules get you part of the way. The long tail of real layouts, every newsletter, form, receipt, and multi-column journal ever printed, is why modern document understanding trains vision models to look at the page the way a person does, instead of reasoning about coordinates.

Those models are a different kind of program. Tesseract is a character-level engine that walks the image with hand-built stages. A transformer OCR model runs a fixed network over an image: here, 333.9M parameters, and a matrix multiply against every one of them for every line it reads. That is millions of multiply-adds, module 3's floats in bulk, with no dependency between them, which is precisely the workload a GPU exists for.

this machine: Apple Silicon GPU (Metal) (mps) — measured on the same scanned page
enginedevicetime unit
TesseractCPU 958.6ms per page
TrOCR (333.9M params)CPU 1.68s per line
TrOCR (333.9M params)mps 412.2ms per line

The GPU runs the same model 4.1× faster than the CPU. Nothing about the model changed. The arithmetic moved to hardware built to do a great deal of it at once.

And be honest about the other column. Extrapolated to a whole page, the ML model costs about 10.7× what Tesseract costs, even on the GPU. This is the trade nobody mentions when they say "just use a modern model": you are choosing to spend one to two orders of magnitude more compute per page, and for a clean printed scan, where Tesseract already gets 0.0005, you would be spending it for nothing. The ML path earns its cost on the documents where the rules fail.

Why it behaves this way

Put the four investigations together and parsing difficulty stops being a vague complaint and becomes a ladder with rungs you can name.

the parsing ladder — each rung needs a different kind of program
the documentwhat it takesstate
text PDF, clean single-column layout read the content stream, honour the specification solved
text PDF, hard layout — columns, tables, forms reconstruct structure from coordinates and whitespace; heuristics, and a table finder that depends on how the document was drawn partially solved
scanned document, clean OCR — a model predicting characters from pixels solved for clean print
scanned document, hard layout or poor quality vision models that read the page as an image, on a GPU open research

Part 0's parse() line silently assumed the top rung. One line, no arguments, no error if the document turns out to be a photograph of a fax. It returns an empty string and the pipeline carries on: it chunks nothing, embeds nothing, indexes nothing, and answers questions about that document by returning some other document, confidently.

That failure mode is the one to take away. Every other stage of the pipeline fails loudly. A missing dependency raises, and a malformed query errors. Parsing fails silently, and it fails per document, so a corpus can be 5% invisible and nothing anywhere will say so. The first thing to build into any ingestion pipeline is the check module 5 and this module both point at: how many characters did each document yield, and which ones yielded none?

Why there is no book for this

Every other stage of your pipeline sits on decades of settled theory. Retrieval has Introduction to Information Retrieval. Storage has Petrov. Encoding has CS:APP. This stage has a nine-hundred-page specification that tells you how to draw a page, and a research literature that is still arguing about how to read one.

That is not an accident. The other stages solve problems somebody designed a format for. This one solves the problem of recovering an intent that was never written down. The document's author knew it was a table, the format had no way to say so, and everything downstream is inference.

How this fits the pipeline

Upward: parse() is a rung on a ladder, and which rung your corpus sits on decides what the rest of the pipeline can possibly do. Backward: module 2 said a file format is an agreement, and that a reader can only recover what the agreement recorded. Here the agreement records pixels. Module 5 measured two libraries disagreeing, and this module gives the mechanisms for why.

meaning is a convention; arrangement is a cost.

A scanned page is the purest statement of the first half on the whole site. The meaning is entirely in the reader, human eye or neural network, and the bytes carry none of it.

Read further, then check yourself

The DocLayNet and LayoutLM papers, introductions only. Readable statements of why layout is a learned problem rather than a rules problem, from the people who built the datasets. Expect DocLayNet's introduction to describe exactly the table you just failed to detect.

The Docling technical report. How a modern open pipeline stages these steps, detecting layout, classifying regions, OCRing what needs it, reconstructing reading order, and where it puts the model that needs a GPU.

There is no canonical book. The papers are the literature. That is worth saying out loud about the pipeline line every tutorial spends the least time on.

  1. A colleague reports that retrieval "doesn't work for some documents". Name the single measurement you would take first, and what its distribution would tell you.
  2. OCR gave 0.0005 on one scan and 0.1277 on another. Both are "scanned PDFs". What would you need to know about a corpus before quoting either number?
  3. The ML model costs about 10.7× Tesseract per page even on a GPU. Describe a corpus where you would pay that, and one where paying it would be waste.
If what you saw didn't match

If pytesseract raises TesseractNotFoundError, remember the Python package is only a wrapper. The engine is a separate binary: brew install tesseract on macOS, apt install tesseract-ocr on Debian and Ubuntu.

If your character error rates are much lower than these across the board, check the dpi you are rendering at. This page's numbers come from rendering the page images at 200 dpi. Feeding OCR a higher-resolution image makes almost everything easier, which is itself the finding: scan quality is a parameter you often control.

If the TrOCR download fails or the processor will not load, run with --skip-ml. Parts (a) to (c) carry the module's argument on their own, and (d) only puts a number on the cost.

If you have no GPU, the CPU timing still makes the point. The model is 333.9M parameters against a hand-built engine, and you will feel the difference. The page reports the machine it ran on; yours will differ, and the ratio between CPU and GPU is what to compare.
