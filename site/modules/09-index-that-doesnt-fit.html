Part III · module 9 · build · 45–70 minutes

09 · When the index doesn't fit in memory

This module breaks module 7's inverted index, and module 4's loading with it. Part II worked because everything fitted in memory. This is the module where that stops being true, and it is the hinge of Part III.

What this module is about

Every structure you built in Part II lived comfortably in memory, and that comfort was doing quiet work for you. A dict lookup assumes the dict is there. Sorting assumes the list is there. Module 7's index assumed the whole corpus could be tokenized into one structure that fits in RAM.

But the index grows in a straight line with the corpus, and your RAM does not grow at all. At some corpus size the two lines cross, and past that point the naive build is not slow, it is impossible. Real search engines index billions of documents on machines that could never hold those indexes in memory, so there must be a technique, and there is. It is old, general, and worth knowing far beyond search: never require the whole structure to exist at once. Build a bounded piece in memory, write it to disk sorted, forget it, repeat, and at the end merge the sorted pieces with a merge that itself only ever holds a sliver. In this module you build that technique, and then you shrink what lands on disk with a compression scheme built from module 3's observation that small numbers need fewer bytes.

The puzzle

Module 7's index held 100,000 passages in 81.3MB. Run the same code at 1,000,000 passages and it holds 574.8MB.

It grows by 596B per passage, and it does not stop. Notice the other thing that broke on the way: at these sizes you can no longer "load the corpus" either.

How do you build an index that is bigger than your memory, using only your memory?

a note on how this module measures Watching a process die is a poor experiment, because when it dies depends entirely on how much memory your machine happens to have. This one measures peak memory at seven corpus sizes for both strategies and plots the curves, so you can read where the line leaves your machine. On the machine that produced these numbers (128.0 GB) the in-memory line reaches physical memory at around 230.6M passages.

Build it yourself

Open exercises/09-index-that-doesnt-fit/starter.py. It has four TODOs: two that stop the index needing memory it does not have, and two that make what is left smaller.

Stream, block, spill, merge

The technique is called SPIMI, short for single-pass in-memory indexing, and it is four rules:

  1. Read documents one at a time. Never hold the corpus.
  2. Accumulate postings in a dict until you have a block's worth of documents.
  3. Write that block to disk as a run of lines sorted by term, then throw the dict away.
  4. When every block is written, merge the sorted runs into one, taking the smallest term available across all the files at each step.

Peak memory is then set by the block size, which you choose, rather than by the corpus size, which you do not.

Then make the postings smaller

A posting list is a sorted list of document ids. Sorted means every id is larger than the one before, so you can store the differences and lose nothing:

The numbers got much smaller, and module 3 already told you that a small number needs fewer bytes. So write each one with as few bytes as it needs. The scheme is called varbyte: seven bits of the number per byte, low bits first, and the eighth bit of each byte says whether another byte follows. Anything under 128 takes one byte instead of four.

Over a 100× range of corpus sizes:

  • the in-memory index grew 47.9×;
  • SPIMI's block-building phase grew 3.1×, because it is bounded by the block size and not by the corpus;
  • SPIMI including the merge grew 15.7×, and that number is worth explaining rather than hiding.

SPIMI costs about twice the wall time, 24.62s against 12.82s at 1,000,000 passages, because it writes everything out and reads it back. That is the price, and it buys a build that does not stop working.

What compression saved, and what it charges

encodingtotal bytes per posting
raw 32-bit document ids 153.8MB 4.00
gaps, still 32 bits each 153.8MB 4.00
gaps, varbyte 53.2MB 1.38

2.9× smaller, from 4.00 bytes per posting down to 1.38.

Look at the middle row, because it is the one that teaches. Converting to gaps saved nothing on its own. The numbers got smaller, but each one still sat in four bytes. The saving came only when the encoding was allowed to use fewer bytes for smaller numbers. Two ideas, and neither works without the other.

And compression charges you back. Reading a posting list that has to be decoded costs 15.4× more than reading a plain Python list of the same postings. Every compressed index in the world makes that trade deliberately: memory and disk are the scarce things, and a few extra arithmetic operations per posting are cheap by comparison.

Why it behaves this way

Start with why the in-memory index grows the way it does. Each new passage adds roughly 40,305,871 ÷ 100,000 postings, around forty, and each posting is a Python integer inside a Python list, which carries far more than four bytes of machinery. Measured, the whole structure costs 596B per passage. Nothing about that is fixable by being careful. It is linear in the corpus, and linear growth against a fixed amount of memory has exactly one outcome.

SPIMI's answer is not to make the index smaller. It is to stop requiring the whole index to exist at once. You hold one block, write it out, and forget it. The finished index is assembled by a merge that reads one line at a time from each block file and writes one line at a time to the output, so the largest thing in memory during the merge is one term's complete posting list, plus one buffered line per file.

Which is exactly why SPIMI's total peak still grew 15.7× while its building phase grew only 3.1×. At a million passages, the posting list for a word like the holds hundreds of thousands of ids, and assembling it means holding it. Real systems stream that too, writing the merged postings out incrementally instead of building the list first. The measurement tells you where the remaining cost is, and it is not where the naive version's cost was.

You have seen this trick before

Look at what spill-and-merge actually is, because it is not new to you.

Module 4 measured that few large transfers beat many small ones, and concluded that you should read in big buffered chunks. This module runs that lesson in reverse. Here memory is the scarce resource instead of time, so you deliberately break one enormous operation into many bounded ones, and the reason that is affordable is module 4's result. Each spill is one large sequential write. Each merge input is one large sequential read. If disk transfers were priced per byte rather than per request, SPIMI would not be worth doing.

Compression is module 3 applied a few million times. Byte widths, and the observation that a small number does not need a large box. Gaps make the numbers small, varbyte lets the small numbers use small boxes, and the 2.9× is the compound interest on a byte-level decision.

How this fits the pipeline

Upward: db.add() at scale does not build the structure module 7 built. It streams, spills, merges, and compresses, and every vector database and search engine you will use does some version of exactly this. Backward: module 4's "few large transfers beat many small ones", run backwards to buy bounded memory; module 3's byte widths, applied 40,305,871 times; module 7's index, which is what broke.

meaning is a convention; arrangement is a cost.

This is the module where the cost stops being a number on a page and starts deciding what you are allowed to build.

Read further, then check yourself

Manning, Raghavan & Schütze, Introduction to Information Retrieval, chapters 4–5. Chapter 4 is index construction under memory pressure, with BSBI and SPIMI named and compared. Chapter 5 is compression, including the gap-and-varbyte scheme you just built and several better ones. Expect chapter 5 to make your 2.9× look modest.

  1. Your block size is 10,000 documents. What happens to peak memory, merge time, and the number of block files if you halve it? Which of those three do you care about?
  2. Gaps alone saved nothing. Say why, in terms of what a 32-bit integer is.
  3. Decoding costs 15.4× more than not decoding. Name a situation where you would refuse to compress, and one where the 2.9× is worth far more than the time.
If what you saw didn't match

If SPIMI's memory grows as fast as the in-memory build, check that your document source is a generator rather than a list. eval_corpus(n) returns a list and holds the whole corpus; iter_eval_corpus(n) streams. Getting this wrong is the most common way to write a streaming index that does not stream, and it is worth causing on purpose once.

If your varbyte round trip fails, the usual cause is the continuation bit. The high bit marks the last byte of a number, not the first. Check the order you emit bytes in, and remember the low seven bits go out first.

If your compression ratio is much better than 2.9×, you may be measuring only the long posting lists. Rare terms have posting lists of one or two entries where gaps save nothing, and they are most of the vocabulary. The ratio over the whole index is always worse than the ratio over the common terms.
