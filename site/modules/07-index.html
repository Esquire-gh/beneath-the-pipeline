Part II · module 7 · build · 40–60 minutes

07 · Index — how search gets fast

This module opens up db.add(), both halves of it. Something was constructed when that line ran. It took time, and it takes up room. This module is about what it is.

What an index is, and why every search engine has one

There are two ways to answer the question "which of these 100,000 passages mention the word block". The obvious way is to read all of them, every time someone asks. The other way is to do that reading once, in advance, and write down the answer for every word at the same time, in a table that maps each word to the list of passages containing it. After that, answering the question means looking up one entry in a table.

That table is called an inverted index, and the list of passages under each word is called a posting list. The name "inverted" describes the flip it performs: documents are stored as "this document contains these words", and the index turns that around into "this word appears in these documents", which is the direction questions actually come from. It is the same move the filesystem made in module 1, where bookkeeping written in advance made a name cheap to resolve. Here, bookkeeping written in advance makes a word cheap to find.

Your pipeline's db.add() built a second structure too: an array of module 6's vectors, arranged so that a query vector can be compared against all of them. In this module you build both structures yourself, measure what they cost to build and to hold, and measure what they give back per query.

The puzzle

Find every passage containing the word block among 100,000 passages by reading all of them. That takes 685.5ms.

Ask the same question of an index and the answer comes back in 0µs.

Nothing about the corpus changed. What exactly did the index precompute, and what did precomputing it cost?

Build it yourself

Open exercises/07-index/starter.py. It has four TODOs, and you are building both of the structures db.add() builds.

about this corpus Every retrieval module from here on runs on a deliberately built corpus: every passage a human judged for relevance, plus a random sample of the rest up to the size you asked for. Taking the first 100,000 lines of MS MARCO instead would leave only 32 of its 6,980 judged queries with their answer in the corpus, and module 8 would have nothing to measure. The construction is in exercises/common.py, function eval_corpus.

The first three TODOs build the inverted index: tokenize each passage, add its id to the posting list of every word it contains, and answer queries by lookup. The fourth builds the other structure, brute-force nearest neighbour over module 6's vectors: score the query against every vector and keep the best ten.

Two things in that table are worth more than the headline ratio.

The scan costs the same whatever you ask. A word in 87,000 passages and a word in none both take about 636.5ms, because the work is reading the corpus, not finding the answer. The index costs about 0µs either way for the opposite reason: it is one table lookup, and the table does not care what is in the bucket.

And the fast scan answers a different question. Searching for block as a substring, which is what grep does, runs in 62.4ms instead of 685.5ms, and returns 805 passages rather than 326. The extra ones contain blockchain, roadblocks, and blocked. Ten times quicker, and not the same query.

What the index cost to build and to hold

structurebuild timesize × the textper query
corpus text itself— 32.1MB 1.00×—
inverted index 1.44s 82.7MB 2.6× 0µs
vectors, brute force none 146.5MB 4.6× 2.4ms

The inverted index holds 125,662 distinct words and 4,024,305 postings, which is 40.2 per passage, and it occupies 2.6× the text it indexes.

The vectors take 146.5MB, which is 4.6× the text, and they cost nothing to "build" because there is no structure, only an array. Every query pays instead: 38,400,000 multiply-adds, every time, for a median of 2.4ms.

At this scale that is completely fine, and it is worth saying so plainly. A 2.4ms query is a fast query. Nothing here needs fixing yet. Module 12 is where it stops being fine.

Why it behaves this way

An index is arrangement. That is the whole definition. You do work in advance to put things where a question can find them, and in exchange the question gets cheap.

Follow where the work went. Building the inverted index took 1.44s. It tokenized every passage, which is exactly what the scan does, but it did so once instead of once per query, and then it wrote the answer down in a shape a lookup can reach directly. The scan repeats that work on every question. The index did it once and kept the result. The 29,925,987× is not cleverness. It is the scan's work, moved to a moment when nobody was waiting.

Which is why the cost shows up in three places, and you measured all three:

  • Time, paid once. 1.44s before any query can run.
  • Memory, paid continuously. 82.7MB, which is more than the corpus itself, held for as long as you want fast answers.
  • Currency, paid on every change. The index describes the corpus as it was when you built it. A new document does not appear in any posting list until something puts it there, and that is module 10's entire subject.

The two structures answer different questions

Look at what the two structures actually organise, because they are not two implementations of one idea.

The inverted index maps words to locations. It answers "which documents contain this token" exactly, and it can answer nothing about a word it has never seen. Ask it for zyzzyva and it says 0, correctly and instantly.

The vector array arranges points for distance. It answers "which documents are nearest this one" approximately in meaning and exactly in arithmetic, and it always returns ten things. There is no such thing as no match, because every point has neighbours. Ask it for nonsense and you get the ten nearest pieces of nonsense.

Those are different failure modes, and neither is a defect. A word index cannot find a paraphrase, and a vector index cannot tell you that a term is absent. Module 15 fuses them precisely because their weaknesses do not overlap.

What db.add() was doing

Now go back to Part 0's line. db.add(ids=…, embeddings=…, documents=…) built exactly these two things: somewhere to look up documents, and an arrangement of points for distance search. It chose the arrangement, the distance measure, the memory layout, and how much accuracy to trade for speed, silently, on your behalf, with defaults that are somebody's answers to questions you can now ask.

How this fits the pipeline

Upward: db.add() has no magic left in it. It is a table of words to locations, and an array of points. Backward: module 1's filesystem keeps bookkeeping so that a name becomes cheap to resolve. This module keeps bookkeeping so that a word becomes cheap to find. It is the same move, at a larger radius.

meaning is a convention; arrangement is a cost.

Here the second half is the whole module, and you have the invoice: 1.44s and 82.7MB, in exchange for 29,925,987×.

Ahead: module 8 asks which ten of the matches to return. Module 9 asks what happens when 82.7MB becomes more memory than you have. Module 12 asks what the vector side costs at a million.

Read further, then check yourself

Manning, Raghavan & Schütze, Introduction to Information Retrieval, chapters 1–2. The inverted index from first principles, and the tokenization decisions that go with it. Expect chapter 2 to spend a surprising amount of time on what counts as a word, and expect to recognise your own tokenize in it.

  1. The scan took about the same time for a word in 87,278 passages and a word in 0. Why? And why doesn't the index?
  2. Your index is 2.6× the size of the text it indexes. Name two things you could store less of, and what each would cost you.
  3. A new document arrives. What has to happen before a search can find it, and what does that suggest about indexing a corpus that changes every minute?
If what you saw didn't match

If your lookup time is reported as 0, you timed one lookup. A single dict access is faster than the clock can resolve. Time 200,000 of them and divide, which is what the solution does.

If your index is much smaller than 2.6× the corpus, check whether you are storing each passage id once per occurrence rather than once per document. Using a set per document before extending the posting list is the fix, and it is why the TODO says each id appears once.

If your speedups are far below 29,925,987×, your scan may be using a substring search rather than tokenizing. That is a fair thing to do, and it is roughly ten times quicker. It also answers a different question, as the block row shows.
