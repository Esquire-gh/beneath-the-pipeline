Part II · module 4 · build · 25–40 minutes

04 · Load — what reading a file costs

This module cashes out loader.load(), the first line of the Part 0 pipeline and the one nobody looks at twice.

What loading means, and why it has a cost

Loading is the plainest stage of the pipeline to describe: bytes sit on the disk, your program needs them in memory, and something has to carry them across. Module 3 made the point that loading changes where bytes are, not what they are. A loaded PDF is still PDF bytes, only now in a place your code can reach.

What makes this worth a module is that the carrying is not free, and its cost has a surprising shape. The cost does not depend only on how many bytes you move. It depends heavily on how the bytes are arranged and on how many times you ask. A library call like loader.load() hides all of those asks behind one friendly name, and in this module you will count them yourself and watch them turn into time.

The puzzle

You have 10,000 small files holding 37.2MB of text. You also have one single file holding the same 37.2MB.

Reading the 10,000 small files takes 65.5× as long as reading the one big one. The bytes are the same, and the disk is the same.

Where did the extra time go?

The mental model: every read is a border crossing

Your program cannot touch the disk. It is not allowed to; only the operating system is. So when you want bytes, you ask, and the ask is a syscall, which is a function call with a border crossing inside it. Your process stops, the processor switches into the mode where the operating system's code runs, that code does the work, and control comes back. The crossing costs something every single time, no matter how few bytes you asked for.

Reading a file takes at least three of these crossings: one to open the file, one or more to read its contents, and one to close it. And the open is the expensive kind, because of what module 1 showed it has to do: read the folder, find the name, fetch the record, get the block list. That work is charged per file, not per byte.

That is the whole module. You are not measuring the disk. You are counting border crossings and watching the bill.

Build it yourself

Open exercises/04-load/starter.py. It has three TODOs, about 30 lines of your own work. You need the corpus first:

Before the TODOs, read the Crossings class at the top of the file. It wraps three calls, os.open, os.read, and os.close, and counts them. That counter is the whole instrument.

Write the three loading strategies

  1. File by file. Open each of the 10,000 files, read it, close it.
  2. One file, small mouthfuls. Open the single large file once and ask for 4 KB at a time. This is what "read it line by line" costs underneath.
  3. One file, one big ask. The same file, 4 MB at a time.

The solution adds a fourth strategy that the starter does not, and it is worth predicting before you look: the same 10,000 files, read with the big buffer. Write down what you expect that to do.

What you should see

Absolute times vary by machine. The column to read is crossings, and the ratio between the top row and the bottom.

measured by exercises/04-load/solution.py — best of 3 runs, 37.2MB moved every time
strategyopensreads crossingstimevs best
file by file, 64 KB buffer 10,000 20,000 40,000 139.3ms 38.1×
file by file, 4 MB buffer 10,000 20,000 40,000 239.7ms 65.5×
one file, 4 KB buffer 1 9,525 9,527 6.9ms 1.9×
one file, 4 MB buffer 1 11 13 3.7ms 1.0×

Three things to have seen:

  • The ratio. There is a 65.5× gap between slowest and fastest, for the same 37.2MB. The crossings ratio is 3,077×.
  • A bigger buffer helped one file and hurt many. On the single file, going from 4 KB to 4 MB was 1.9× faster. On the 10,000 files, the same change was 1.7× slower. If your model of the problem is "use a bigger buffer", that second result has no explanation.
  • Cost per crossing is not constant. File-by-file spent 3.48 µs per crossing, while the small-buffer read spent 0.72 µs. Not all crossings cost the same, and the expensive ones are the ones that involve the filesystem's bookkeeping.

And the disk barely participated

Every number above was measured with the data already in memory. The operating system keeps recently read blocks in a page cache, so a second read does not touch the hardware. Run it again with that cache bypassed and almost nothing changes:

File-by-file went from 139.3ms warm to 150.5ms cold. The whole 65.5× penalty survives with the media taken out of the picture, because it was never about the media.

Why it behaves this way

Work backwards from the crossings column, because it explains every row.

Reading 10,000 files cost 40,000 crossings: 10,000 opens, 20,000 reads, and 10,000 closes. That is two reads per file, because you cannot know you have reached the end until a read comes back empty. Reading the same bytes from one file cost 13 crossings in total.

Now recall from module 1 what an open actually does. It reads the folder's contents, finds the pair whose name matches, takes the record number, reads that record, and gets the list of blocks. That is real work, and it is charged per file, not per byte. It is why the two file-by-file rows cost about the same as each other regardless of buffer size: the buffer was never the expensive part.

So why was the big buffer slower on many files? Because asking for 4 MB from a 3.8KB file still means preparing to receive 4 MB. The runtime sets aside that much room, the kernel copies 3.8KB into it, and the rest of the preparation is wasted, 10,000 times over. A buffer is a bet about how much data is coming. Bet too small and you pay in crossings. Bet too large and you pay in preparation. Neither is free, which is why "increase the buffer size" is not advice on its own.

The single-file rows show the other half. Going from 4 KB to 4 MB cut crossings from 9,527 to 13 and cut time by 1.9×. Here the buffer was the only variable, so making it larger did exactly what it should.

What loading actually is

Put the whole thing in one list, and notice that no step is mysterious:

  1. Consult the database the operating system keeps about your bytes, first the folder and then the record, to find which blocks belong to this file. That is module 1.
  2. Ask for those blocks, in as few crossings as you can manage.
  3. Decode the bytes under an agreed convention. That is module 2, and it is where a wrong guess about encoding enters your corpus.
  4. Hold the result in memory.

That is loader.load(). There is no fifth step. What a library adds is defaults for the choices in steps 2 and 3, namely how much to ask for at a time and which encoding to assume, and it does not tell you what it chose.

One consequence is worth carrying forward. A corpus arriving as 10,000 files is not the same problem as a corpus arriving as one file, even when the bytes are identical. Every production ingestion pipeline you will meet has an answer to this, usually "combine small files into large ones before doing anything else". Now you know what that is buying.

How this fits the pipeline

Upward: the first line of the Part 0 pipeline is a folder lookup, a record read, some number of block requests, and a decode. You can now count each of those, and you know which one dominates. Backward: module 1 said the filesystem keeps bookkeeping about your bytes. This module is the invoice for consulting it 10,000 times.

meaning is a convention; arrangement is a cost.

The bytes were arranged as 10,000 files instead of one. Nothing about their meaning changed. The cost changed by 65.5×.

Module 9 runs this lesson backwards: when an index is too large to hold in memory, you deliberately write it out in pieces and merge them, and the reason that works is this same arithmetic. Few large transfers beat many small ones.

Read further, then check yourself

Petrov, Database Internals, Part I. Read it for one thing: how storage engines batch their work specifically to stay off the boundary you just measured. Expect the phrase "one large file" to keep appearing, and now you will know why.

  1. Your corpus is 37.2MB either way. Explain, in terms a colleague could act on, why the arrangement into files changed the cost by 65.5×.
  2. A 4 MB buffer helped on one file and hurt on 10,000. Give the rule that predicts both.
  3. You are handed a corpus of a million 2 KB files. Name the first thing you would do, and what it costs you.
If what you saw didn't match

If your ratio is under 5×, your files may be larger than this corpus's 3.8KB average. The per-file cost is fixed, so the bigger each file is, the less it matters. Check data/corpus_small/.complete for the size the corpus was built at.

If the big buffer does not slow down the many-files case on your machine, that is a legitimate difference: it depends on how your runtime allocates the receiving buffer. The crossing counts will still be identical between those two rows, and that identity is the finding. The buffer changed nothing about the number of asks.

If --cold makes no difference at all, you are on Linux, where F_NOCACHE does not exist and the flag is ignored. Drop the cache with sync && echo 3 | sudo tee /proc/sys/vm/drop_caches instead, or skip it, since the warm numbers already carry the argument.
