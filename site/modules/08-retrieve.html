Part II · module 8 · build · 60–90 minutes

08 · Retrieve — how results get ranked

This module opens up retrieve()'s silent ranking, and asks the question every tutorial skips: how would you know if the ranking is bad?

What ranking is, and why it needs measuring

Module 7 made finding cheap. Ask the index for a word and it hands you every passage containing it, instantly. But "every passage containing it" is thousands of passages, and the user gets ten. So something has to put the thousands in order, and that something is a scorer: a function that takes the query and a document and returns a number, where a higher number is supposed to mean more relevant. Sort by the number, return the top of the list, and that is retrieval.

The whole question is what function to use. In this module you build four, in increasing order of sophistication: counting the query's words in each document, weighting those counts by how rare each word is, the tuned version of that idea the field settled on after forty years, and module 6's cosine similarity over vectors.

And then you build the more important thing, which is the instrument that says whether any of them works. Ranking functions are easy to have opinions about and hard to be right about, so the field measures them: take real queries where a human has marked which passage answers each one, run the scorer, and check where the marked passages landed. The second half of this module builds that harness, and the harness is what every later module in the site uses to keep itself honest.

The puzzle

A median query in this corpus matches 41,070 passages. Some queries match 98,758.

The pipeline returns 10 of them.

Which 10, decided by whom? And if the decision were bad, how would you ever find out?

Build it yourself

Open exercises/08-retrieve/starter.py. It has five TODOs: three scorers, then the two measurements that tell you whether a scorer is any good. The measurements are the module.

Write three scorers

Start with the obvious one: add up how often the query's words appear in each document. Then write tf-idf, which fixes two things at once. It damps repeated occurrences, so the tenth counts for less than the first, and it weights each word by how rare it is, because a word in every document tells you nothing. Then write BM25, the same two ideas tuned by forty years of measurement, with two knobs: k1 for how fast extra occurrences stop helping, and b for how hard long documents are penalised.

Then build the measuring instrument

Build the harness. Precision@10 asks what fraction of the ten you returned were relevant. NDCG@10 asks the same thing but pays more for being right early, discounting each position logarithmically. Both need relevance judgments, which are records of a human saying, for a real query, which passages actually answer it. MS MARCO ships 6,980 of them for this corpus, which is the reason the site uses it.

What raw term counts actually gets wrong

The textbook complaint is that long documents win. Check it here before repeating it. These passages run from 35 tokens at the tenth percentile to 93 at the ninetieth, and the top ten by raw term count average 59 tokens against a corpus average of 58. On this corpus, there is no length bias to see. The passages are too uniform for it to bite.

So the collapse to 0.0872 has a different cause, and it is measurable: 53% of a raw term-count score comes from stopwords. Words like the and of appear in almost every passage, many times each, so a scorer that counts occurrences is mostly ranking by how often a document says "the".

The changes that sound better and rank worse

the changethe reasoningNDCG@10Δ
drop stopwords"stopwords are noise" 0.6881 0.0052
raise k1 to 2.5"reward repeated terms more" 0.6480 -0.0349
set b to 0"stop penalising long documents" 0.6471 -0.0357
set b to 1"penalise long documents fully" 0.6749 -0.0080

3 of 4 plausible improvements made the ranking worse. Every one of them has a story you could tell a colleague, and three of the four stories are wrong on this corpus. Notice also that the one change that helped, dropping stopwords, helped by 0.0052, which is smaller than the damage any of the others did.

That moment is the point of the module. Without the harness, all four of those changes ship.

Why it behaves this way

Work backwards from the collapse. Raw term counts scored 0.0872 because it treats every word as equally informative, and 53% of the words in a query are not informative at all. tf-idf fixed that with one idea, weighting each word by its rarity, and the score went to 0.6138. A word appearing in every document gets a weight near zero, so the stops voting.

BM25 added the second idea. Occurrences should have diminishing returns, because a document saying "block" ten times is not ten times more about blocks than one saying it once. k1 controls how fast that curve flattens, and b controls how much a document's length discounts its term counts. Those two knobs took the score to 0.6829. BM25 also ran faster here, 39.6ms down to 1.6ms per query, because the vectorised version does one array operation per query term.

Then the vectors. Dense retrieval scored 0.8704, and it does something the word scorers structurally cannot: it finds passages that answer the question in different words. It also costs 4.2ms per query against BM25's 1.6ms, because it compares against every vector in the corpus. Module 12 is about buying that time back and what the purchase costs.

Relevance is measured, not asserted

Here is the sentence to take out of this module.

Every ranking decision you make is a hypothesis. "Rare words matter more" is a hypothesis. "Long documents should be penalised" is a hypothesis. "Dense beats sparse" is a hypothesis. Each one is plausible, each one has a mechanism behind it, and you just watched three plausible hypotheses with good mechanisms behind them make things worse.

Without judgments, you cannot tell the difference between a change that helped and a change you like. You tune by anecdote: you try a query you remember, the result looks better, you ship. The harness replaces that with a number over 1,000 queries you did not choose.

It has limits, and they are worth stating. NDCG@10 on MS MARCO measures one population of queries against one set of judgments, and a system that wins here can lose on your documents. The judgments are sparse. Most queries have exactly one passage marked relevant, so a genuinely good answer that nobody judged counts as a miss, which is why absolute P@10 looks low even for the best scorer. The right conclusion is not "0.68 is the truth" but "these two systems were compared on the same 1,000 queries and one won".

This harness is the instrument for the whole of Part III. Modules 11, 12 and 15 all import evaluate and ndcg_at_k from your solution file, because every claim they make about speed has to be paired with what it did to quality.

How this fits the pipeline

Upward: retrieve(db, model, q, k=4) ranks by cosine similarity, silently, and returns four. You now know what the alternatives are, roughly what each scores, and how to find out for your own corpus. Backward: module 7 built the arrangement, and this module chose what to do with what it finds. Module 6's cosine is now one scorer among several rather than the definition of relevance.

meaning is a convention; arrangement is a cost.

And a third thing, which the site says once, here: quality is a measurement. Everything after this module reports what it did to NDCG.

Read further, then check yourself

Manning, Raghavan & Schütze, Introduction to Information Retrieval, chapters 6–8. Chapter 6 is the weighting you just built, and chapter 8 is the evaluation you just built, including why precision and recall pull against each other. Expect chapter 8 to be more careful than this page about what a judgment does and does not mean.

  1. Raw term counts scored 0.0872 on a corpus with no length bias. Explain the failure without using the phrase "long documents".
  2. Setting b to 0 and setting it to 1 both lowered NDCG. What does that tell you about the default of 0.75, and about tuning by intuition?
  3. Your P@10 is 0.0871 while MRR@10 is 0.6487. Why are those so far apart, and which one would you report to a colleague?
If what you saw didn't match

If every scorer reports NDCG near 0, your document ids are probably not lining up. The judgments name MS MARCO passage ids, and your scorers rank corpus positions. The starter builds pid_to_doc for exactly this; make sure the relevant set is mapped through it before comparing.

If BM25 scores below tf-idf, check the sign inside the idf logarithm. log(1 + (N - df + 0.5) / (df + 0.5)) stays positive for every term. The older form without the 1 + goes negative for terms in more than half the corpus, and those negative weights will scramble your ranking.

If your absolute numbers are higher than this page's, you may be scoring fewer queries. The first few hundred qids are not a random sample, so compare like with like: same query count, same corpus size.

If dense retrieval loses to BM25 on your machine, that is a legitimate result on a different corpus and a reason to read the caveat above again. On MS MARCO with this model, expect dense to win.
